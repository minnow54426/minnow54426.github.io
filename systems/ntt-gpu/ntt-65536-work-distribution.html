How 65,536 coefficients
map to GPU threads.

See how our 65536-point forward and inverse NTTs distribute data and butterflies. Start with what a block owns, then zoom into what a thread does.

01

Start with the data

Consider one polynomial modulo one prime: a[0], a[1], …, a[65535]. Each residue uses 8 bytes, so one RNS limb occupies 512 KiB.

65536coefficients per modulus
16stages · 32768 butterflies each
524,288butterflies · two kernel launches

Imagine the same array as 256 rows × 256 columns. This is an index view; the stored array stays flat.

global_index = row × 256 + column
02

Divide the work by distance

Pass 1 · far stages

One block owns one column

32768 → 16384 → 8192 → 4096 → 2048 → 1024 → 512 → 256

These distances preserve the index modulo 256. Each block gathers 256 strided values into shared memory, executes eight stages, and scatters the results back.

256 blocks per modulus. Every block launches 256 threads: 256 load/store values; 128 compute butterflies at each stage.

256 values · 2 KiB shared memory / block
Pass 2 · near stages

One block owns one row

128 → 64 → 32 → 16 → 8 → 4 → 2 → 1

These butterflies stay inside an aligned 256-value row. Each block loads its contiguous row into shared memory, executes eight stages, and writes it back.

256 blocks per modulus. All 256 threads load/store values; 128 compute butterflies at each stage.

256 values · 2 KiB shared memory / block

Both passes use twiddles from the same 65536-point transform. Threads 128–255 still load, store, and reach every barrier, even when they have no butterfly.

Resources & memory access

Pass 1: column 3, thread 5

Block 3 gathers values[3 + 256 × t] into shared[t], for t = 0…255. Thread 5 loads position 1283. At global distance 32768 (local distance 128), it computes shared positions 5 and 133: global positions 1283 and 34051. At distance 256 it computes 2563 and 2819 instead.

Pass 2: row 3, thread 5

Block 3 loads positions 768…1023. At distance 128, thread 5 computes 773 and 901; at distance 1, it computes 778 and 779. The final row, block 255, owns positions 65280…65535.

Read the memory access map

In pass 1, adjacent loading threads access global addresses 2048 bytes apart (256 × 8 bytes), but write adjacent 8-byte entries in shared memory. The scatter reverses this mapping. In pass 2, adjacent threads read and write adjacent 8-byte global entries. Each block loads once, reuses shared memory across all its stages, and stores once.

Two reads and two writes of the value array give a logical minimum of 4 × N × 8 bytes per forward transform: 2 MiB at N=65536, excluding twiddle/modulus reads and host transfers. This is requested array traffic, not measured DRAM traffic. Strided accesses, caches, registers, and occupancy need real-GPU profiling; 128 active butterfly threads out of 256 is not a hardware occupancy measurement.

Source map: CUDA kernels and launchers define the grid and gather/scatter; stage helpers map threads to pairs. For N=65536, the gather uses r + 256 × local_index; near-stage access uses row × 256 + local_index. Within each stage, every position belongs to exactly one butterfly.

04 · D2

Why these inputs and twiddles?

Our forward butterfly has two multipliers. Let ψ be the primitive 2N-th root modulo the current prime q. The ladder multiplier is \(c=\psi^d\); the difference-leg multiplier is \(w=\psi^E\). Both are powers from the global transform, not a smaller column NTT.

\[a=\mathrm{values}[U],\quad b=\mathrm{values}[V],\qquad x=a+cb,\quad y=(a-cb)w\pmod q.\]

The folded twist remains inside every butterfly

\[c=\psi^d,\quad w=\psi^{(N/d)J},\qquad x=a+cb,\quad y=(a-cb)w\pmod q.\]

At N=65536, the first column stage has d=32768 and c=ψ³²⁷⁶⁸. At the last column stage d=256, c=ψ²⁵⁶. The row pass continues the same transform with d=128 down to 1. It does not reset ψ or N.

How the last two row stages finish the transform
Stage (zero-based)d / offset JFactorsOutputs
142 / 0 or 1c=ψ²; w=1 or ψ³²⁷⁶⁸Two size-2 children per size-4 group
151 / 0 onlyc=ψ; w=1Upper=a+ψb; lower=a−ψb

The last layer has no difference-leg multiply by a nontrivial w, but the lower input still carries ψ. Removing c would change the transform to the wrong ring. Final outputs are already in bit-reversed evaluation order. The derivation and full numerical network explain how the original coefficient twist is distributed through these stages.

1. Decode a thread into a local pair

The split width B is 256. Column r is blockIdx.x; p is the butterfly index. At N=65536, each active thread processes just one pair per stage, so p = threadIdx.x. More generally the stage helper loops over p = threadIdx.x + k × blockDim.x. Let δ be the local distance; the global distance is d = B × δ.

\[\begin{aligned}g&=\lfloor p/\delta\rfloor,&j&=p\bmod\delta,\\u_{\rm local}&=2\delta g+j,&v_{\rm local}&=u_{\rm local}+\delta,\\U&=B u_{\rm local}+r,&V&=Bv_{\rm local}+r=U+d.\end{aligned}\]

2. Recover the CPU group and offset

Substitute the local pair into the global index:

\[\begin{aligned}U&=B(2\delta g+j)+r\\&=2dg+(Bj+r),\\\text{group start}&=2dg,\qquad J=Bj+r.\end{aligned}\]

Because 0 ≤ j < δ and 0 ≤ r < B, we have 0 ≤ J < Bδ = d. Thus U and V are exactly the CPU pair at offset J in group g. Conversely, every CPU offset has a unique decomposition J = 256j + r. Together with p = gδ + j, this gives one unique column/thread owner for every CPU butterfly.

3. Prove the exponent, not just the result

The CPU starts w at 1 for each global group and multiplies it by \(\psi^{N/d}\) after each offset. At offset J it therefore uses \(w=\psi^{(N/d)J}\). Substitution gives:

\[c=\psi^d,\qquad E=\frac Nd(256j+r),\qquad w=\psi^E.\]

This is precisely the stage helper: if ℓ = log2(δ), then δ << 8 = d, N >> (8 + ℓ) = N/d, and (j << 8) | r = 256j + r. The OR equals addition because r occupies only the low eight bits. Also 0 ≤ E ≤ N − N/d < N, so the power-table access is in range.

A subtle point: thread 0 in column 3 has J = 3, not 0. Its w is generally not 1. Only J = 0 gives exponent 0. The ladder c and w are distinct: the negacyclic ladder remains even when w = 1.

5. An exhaustive executable check

column_mapping_tests.cpp enumerates every CPU group/offset in every column stage at N=65536. It executes the actual dev_dif_col_stage body with synthetic tagged power tables. An upper-input probe reveals the selected w exponent; a lower-input probe checks the ladder and both destinations. Whole-column comparisons catch unintended writes. The test also checks unique coverage and every inactive thread.

There are 262,144 column butterflies at N=65536: 262,144 pairs and 524,288 active-pair probes. Tagged tables are diagnostic values, not valid root powers. The separate schedule gate checks real-root forward arrays, round trips, and multiplication. Both checks run on CPU; neither validates CUDA launch behavior or GPU races.

05 · D3

Undo the forward butterfly

The inverse-column helper dev_dit_col_stage uses the same pair mapping as D2. Only the arithmetic and stage order change. It reads an inverse-power table: entry e is (ψ⁻¹)^e. The exponents d and E stay positive; we do not use negative table indices.

Forward · DIF

\[\begin{aligned}c&=\psi^d,\quad w=\psi^E,\\x&=a+cb,\\y&=(a-cb)w.\end{aligned}\]

Inverse · DIT (unscaled)

\[\begin{aligned}t&=yw^{-1},\\a^{\prime}&=x+t,\\b^{\prime}&=(x-t)c^{-1}.\end{aligned}\]

All operations are modulo the limb prime q. Substitute the forward outputs into the inverse:

\[\begin{aligned}t&=(a-cb)ww^{-1}=a-cb,\\a^{\prime}&=(a+cb)+(a-cb)=2a,\\b^{\prime}&=((a+cb)-(a-cb))c^{-1}=2b.\end{aligned}\]

So the inverse first untwiddles the difference leg by w⁻¹, then forms the sum/difference, then multiplies the lower result by c⁻¹. Swapping those multipliers or omitting either one is incorrect. To recover a and b from just one butterfly, divide both results by 2 modulo q.

Why scale only once?

Every coefficient traverses log₂N butterflies. Each reversed stage contributes a factor of 2. These factors commute with every stage because the operations are linear modulo q. Thus the entire unnormalized inverse of the forward transform gives 2^(log₂N) × input = N × input.

recovered[i] = unnormalized_inverse[i] × N⁻¹ mod q

The modulus q is an odd prime and N is a power of two, so N has an inverse modulo q. Our code applies inverse_scale_kernel once at the end, using the inverse length for the selected RNS limb—not floating-point division and not a separate coefficient twist.

Reverse the execution, not the array

Forward column distances decrease, then forward row distances decrease. The inverse reverses that sequence: row distances increase, then column distances increase, then normalization. Gather/scatter addresses, grid sizes, shared-memory sizes, and active-thread ranges are unchanged for each data subset.

A small numeric butterfly

For arithmetic only, take N=8, q=17, ψ=3, d=2, J=1: E=4, c=9, w=13. Let a=4 and b=5. Forward gives x=15, y=11. Since w⁻¹=4 and c⁻¹=2, inverse gives t=10, a′=8, b′=10, exactly 2a and 2b modulo 17. What the D3 checks establish

inverse_column_check executes the real inverse-column helper on CPU. It checks every column pair at N=65536 with tagged tables (262,144 pairs, two basis-input probes each), and every inactive thread. With valid roots for two 46-bit primes, it checks DIT(DIF(stage)) = 2 × input at every column stage and column. A full near→far inverse fed by the independent CPU forward transform must equal N × input before scaling and the original array after scaling.

These checks establish the shared stage arithmetic and CPU-reproduced ordering. They do not compile CUDA, exercise actual launch/barrier behavior, or measure GPU performance. The D4 section below examines contiguous kernels and stage coverage in detail.

06 · D4

Why two passes equal the full transform

The column proof handles far stages. The remaining kernels—forward_contiguous_tile_kernel and inverse_contiguous_tile_kernel—assign one contiguous tile to each block. For our target sizes, tile length L is 256; for smaller transforms it is min(256,N).

1. Map a row thread to the CPU pair

Let b be the row block, p the pair index, and d a near-stage distance (128 down to 1 for forward, 1 up to 128 for inverse). Each active thread has p = threadIdx.x for these tiles.

\[\begin{aligned}g&=\lfloor p/d\rfloor,\quad j=p\bmod d,\\u_{\rm local}&=2dg+j,\quad v_{\rm local}=u_{\rm local}+d,\\U&=Lb+u_{\rm local},\quad V=U+d,\\\text{group start}&=Lb+2dg,\quad J=j,\quad E=(N/d)j.\end{aligned}\]

Why is this a valid CPU group? Since d is a power of two and 2d ≤ L, 2d divides L. Therefore Lb + 2dg is a multiple of 2d, exactly where the CPU group loop begins. Also 0 ≤ j < d and the final local lower index is at most L−1. Every CPU group fits entirely inside an aligned tile.

Notice what disappears: the row number b does not appear in J or E. Moving to another aligned row changes the group number, not the offset within that group. But N still appears: these are global-transform powers, not the twiddles of an independent 256-point NTT.

\[\begin{aligned}\text{Forward: }&c=\psi^d,\quad w=\psi^{(N/d)j},\\\text{Inverse: }&c^{-1}=(\psi^{-1})^d,\quad w^{-1}=(\psi^{-1})^{(N/d)j}.\end{aligned}\]

3. Account for every stage exactly once

The CPU distances are precisely the powers of two from N/2 down to 1. At N≥512, they partition into two disjoint sets:

\[\begin{aligned}\text{Far: }&d=32768,16384,\ldots,256,\\\text{Near: }&d=128,64,\ldots,1.\end{aligned}\]

Forward runs far distances descending, then near distances descending. Inverse reverses both passes and scales by the inverse of 65536. For other supported N≥512, far distances begin at N/2.

There is no missing distance between 128 and 256: no power of two lies between them. Neither set overlaps the other. The far count is log₂N − 8; the near count is 8. Each stage has exactly N/2 disjoint butterflies, so the full count is (N/2) × log₂N per direction. Scaling is not an additional butterfly stage.

N=65536 · forward and inverse share these stage counts
NFar + near stagesTotal butterflies / direction
655368 + 8 = 16524,288

At N≤256, the far pass is skipped and one tile covers all log₂N stages. The coverage check also exercises N=2, 64, 256 and 512, including the tile clamp and first column-pass boundary.

4. Why block-local stage fusion is safe

During all far stages, every dependency stays inside the same column; during all near stages, every dependency stays inside the same tile. A block may therefore finish all its stages before another block finishes its first: those blocks do not consume each other's intermediate values within that pass. This reorders independent operations without changing the CPU result.

Each tile loads values[Lb+t] into shared[t]. All threads reach the load barrier and every stage barrier. Threads 0…127 compute butterflies at L=256, while all 256 threads participate in loading/storing and synchronization. The block stores its tile once after the last stage. Within a stage, pair endpoints do not overlap; between stages, the shared-memory barrier makes the preceding writes visible.

The dependency rule changes between passes. Results must be scattered before the next pass gathers them; our same-stream kernel sequence provides that boundary. Thus gather/scatter is a change in block ownership, not a transpose or extra arithmetic transform. Together with D2/D3's identical pair arithmetic, exact ordered stage coverage establishes equivalence to the CPU transform.

5. Executable evidence

tile_mapping_check runs the actual row-stage helpers on CPU, comparing against independent CPU group/offset enumeration. At N=65536 it checks every row, stage and pair in both directions, using two tagged-table input probes per pair, plus inactive-thread checks. That is 262,144 pairs per direction and 1,048,576 active probes in total.

The same test checks forward and inverse stage lists and per-stage global endpoint coverage at N=65536, plus the small-size boundaries. Existing real-root schedule and inverse-normalization gates remain complementary checks. This is not a CUDA compile, barrier/race check, or GPU performance measurement.

08

What keeps the work ordered?

Inside a block

All 256 threads reach __syncthreads() after loading and after each stage—even threads without a butterfly. This barrier synchronizes only that block.

Between the passes

The kernels use the same CUDA stream, so pass 2 starts after pass 1 finishes. Blocks within a pass are independent; SM scheduling does not guarantee they all execute simultaneously.

For CKKS with multiple RNS primes, repeat this arrangement per limb. Storage is limb-major: values[limb × N + index]. blockIdx.y selects the limb; blockIdx.x selects the column in pass 1 or the row in pass 2.

The mental model: a block owns a data subset; a thread computes a butterfly within it at each stage. Next, follow the constructor, buffers, and host/device dataflow (D5).
