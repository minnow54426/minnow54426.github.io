Integration roadmap

Read the sequence of work and the checks required to finish each phase.

At a glance

  • Build the NTT first, then prime-basis conversion, Hybrid key switching and OpenFHE integration. D labels a working milestone, not a calendar date.
  • D11/P2 remains open. The current Ada batch passed, while RTX 5090 acceptance, driver/context failure handling and hardware counters remain pending.

Before you start: Start with the live tracker. D labels working milestones, not calendar dates.

Detailed guide

Build in this order: NTT → base conversion → Hybrid key switching → OpenFHE. The Number Theoretic Transform (NTT) helps multiply polynomials by turning that task into separate products at special evaluation points. Base conversion changes which primes represent each coefficient. Hybrid key switching combines these operations with evaluation-key arrays to change a ciphertext’s key representation without decrypting it.

The estimate is 95 working days plus 15 reserve days. D labels a working-day milestone and P labels a phase; neither is a calendar date or a continuous rental period. Preparation may happen early, but a phase closes only after its acceptance checks pass.

Target OpenFHE 1.6.1, N=65536, RTX 5090 primary and RTX 4090 control. Baseline benchmarks also span N=4096–65536 and 30/50/55/60-bit primes in uint64_t. Last reviewed: 2026-11-23 (Asia/Shanghai).

Definition of exact compatibility¶

Use the same parameters, input arrays, ciphertext components and evaluation keys in both programs. The GPU must then produce exactly the same values in every prime tower as the selected OpenFHE version. CKKS decrypts to approximate numbers, so similar decrypted answers are a useful second check but cannot prove exact array compatibility. Generate a key once and use those same key arrays for both paths; independently generated random keys are different inputs. The concrete upstream path is NativePoly::SwitchFormat for transforms and KeySwitchCore → EvalFastKeySwitchCoreExt → ApproxModDown for Hybrid contributions.

Every production kernel must pass, in order:

  1. arithmetic primitive versus the __uint128_t oracle;
  2. operation versus this repository's CPU reference;
  3. operation versus pinned OpenFHE 1.6.1;
  4. full pipeline versus OpenFHE using fixed inputs and keys;
  5. benchmark/profiler gate on named hardware.

P2 — first real GPU baseline (D11–D15)¶

The November 14 temporary Ada batch passed 29 native CTests, eight sanitizer runs and 280 GPU timing jobs. A separate M1 Pro baseline covered 140 CPU jobs. The reported GPU was RTX 4080 SUPER/compute 8.9, not the primary RTX 5090 or planned RTX 4090 control. Hardware counters were blocked by the provider.

Later offline preparation and the resident-chain prototype pass host tests and sm_89/sm_120 compilation. The November 19 batch then passed the new resident, Shoup and conversion checks on reported compute 8.9. Both schedules passed their native gates and 40 sanitizer stages across the pair. All 48 paired measurement jobs, four resident repeat runs and a CUDA timeline were exported and verified locally. Primary-device acceptance, actual driver/context failure handling and hardware-counter profiling remain open.

November 20 preparation adds resident ModUp/ModDown composition. CPU/OpenFHE checks, failure tests and both CUDA schedule builds pass locally. The new conversion fixture is part of the existing native resident gate and its sanitizer smoke. That later code still needs a real GPU run. The November 19 performance analysis also awaits its raw archive in this workspace.

Next session: run the current native checks, resident sanitizer scope and per-pass profiling on an actual RTX 5090. Use the split collector for GPU-only measurements and collect the CPU baseline locally.

Dispatch policy:

invalid input or inconsistent format    -> error
valid same-format request               -> validated no-op
available + supported + verified        -> CUDA backend
unavailable/unsupported/unverified      -> CPU only if allowed before submission
busy/budget/allocation failure          -> visible resource error
submission attempted, then any failure  -> visible error; no automatic CPU retry

The opt-in adapter defaults to RequireDevice. See ADR 0001 for the accepted transaction, ownership, cache-budget and admission rules. Production integration remains a P8 gate.

P8 exit gate:

  • OpenFHE CKKS runs with Hybrid key switching through the GPU backend.
  • Original CPU tests and fallback remain green.
  • NTT, base conversion, relinearization, and rotation meet exact gates.
  • Constants and evaluation keys remain resident across operations.
  • All results identify hardware, clocks/power mode, driver, toolkit, compiler, commit, parameters, timing boundary, and correctness status.

P9 — risk reserve (D96–D110)¶

Use only for work that blocks a preceding exit gate:

  • OpenFHE rounding/reduction-order differences;
  • natural/bit-reversed ordering mistakes;
  • CKKS level/tower corner cases;
  • register spilling, shared-memory pressure, or poor occupancy;
  • evaluation-key memory pressure and cache eviction;
  • CUDA stream/event lifetime defects;
  • primary-GPU compiler or architecture problems;
  • cross-GPU dispatch regressions.

Do not schedule new features in the reserve. Running an encrypted inference model begins only after P8’s checks pass. That needs a separate plan for model operations, scale changes, rotations, execution order, numerical accuracy and the time for a complete request.
