CKKS GPU-to-OpenFHE integration plan¶

Target: OpenFHE 1.6.1 CKKS with Hybrid key switching
Primary arithmetic: 50–60-bit RNS primes stored in uint64_t, with uint32_t indexing/control paths where safe
Ring dimension: 65536
Estimate: 95 planned working days + 15 risk-reserve days
Last updated: 2026-11-14 (Asia/Shanghai)

Follow the live tracker, then open the phase you need from the section sidebar. The sequence is NTT → base conversion → Hybrid key switching → OpenFHE. Update this tracker only when a deliverable passes its gate.

Definition of exact compatibility¶

Given the same parameters, input arrays, ciphertext components, and evaluation keys, the GPU path must produce the same per-tower arrays as the pinned OpenFHE implementation. Approximate CKKS decryption agreement is a secondary test, not the compatibility criterion. Key generation randomness is outside this rule; the fixed generated key is part of the test input. The concrete upstream path is NativePoly::SwitchFormat for transforms and KeySwitchCore → EvalFastKeySwitchCoreExt → ApproxModDown for Hybrid contributions.

Every production kernel must pass, in order:

  1. arithmetic primitive versus the __uint128_t oracle;
  2. operation versus this repository's CPU reference;
  3. operation versus pinned OpenFHE 1.6.1;
  4. full pipeline versus OpenFHE using fixed inputs and keys;
  5. benchmark/profiler gate on named hardware.

P0 — pre-plan baseline (DONE)¶

  • Negacyclic CPU NTT and Python big-integer oracle.
  • Shared CPU/CUDA stage bodies and portable schedule simulator.
  • Correctness-first two-pass CUDA source.
  • Exact public OpenFHE 1.6.1 transform compatibility for all target N.
  • RTX 4090/5090 build targets and rented-GPU setup script.
  • Benchmark and tuning methodology.
  • Execution of CUDA gates on real hardware; this belongs to P2.

D1 complete: the interactive work-distribution map covers N=65536, gather/scatter and shared-memory indices, launch geometry, active thread ranges, and requested memory-access patterns. This is a source analysis and CPU-schedule check, not evidence of real-GPU correctness or speed.

D2 complete: the same page's column proof derives CPU group/offset equivalence, both global exponents, coverage, bounds, and three worked examples. column_mapping_check runs the production stage body with two tagged-table probes for every column butterfly at N=65536; the separate schedule gate checks real-root arrays. Real-GPU validation is still a P2 deliverable.

D3 complete: the inverse proof derives the factor of 2 per butterfly and final N-inverse normalization, documents row→column→scale ordering, and provides worked examples. inverse_column_check probes every inverse column pair and inactive thread at N=65536, then checks real-root stage composition and full normalization for two 46-bit primes. These are CPU-side checks of shared helpers, not actual GPU execution.

D4 complete: the row-kernel and coverage proof derives tile-local/global group equivalence and global twiddle exponents, proves the far/near stage partition and legal block-local stage fusion, and provides worked examples. tile_mapping_check probes every near-stage pair in both directions at N=65536 and checks stage/endpoint coverage for N=65536 plus N=2,64,256,512. Hardware races and CUDA launch behavior remain P2 work.

D5 complete: CUDA buffers and dataflow maps the constructor, all six device allocations, normal destruction, per-method copies, launch composition, representation ownership and missing integration contracts. Static source checks pin this map and byte-count arithmetic; they are not CUDA-runtime tests. D5 identified a raw-Impl constructor exception gap. Later offline preparation changes it to unique ownership, adds device guards and checks host inputs, and compiles the wrapper. Native failure-path verification and the production resident runtime remain open.

D6 complete: Arithmetic bounds and tests records canonical-range induction, integer-width bounds, parameter preconditions, the exactness ladder and deferred adversarial cases. Two CPU gates compare 14,956 primitive results against Python big integers and exercise six patterns in both transform directions plus a closed-form negacyclic product at N=65536 with 50/55/60-bit primes. The multiplication-count comment is corrected; arithmetic algorithms are unchanged. Native GPU and invalid-input hardening remain explicit later gates, not evidence claimed by this review.

D7 complete: the OpenFHE representation contract traces pinned NativePoly/DCRTPoly format conversion, exact odd-root evaluation indices, minimum-root selection and its cache constraint, canonical residues, ordered tower packing/import, and active-prefix behavior. A new opt-in core-only gate checks full-size formulas and three-tower operations with 50/55/60-bit primes against OpenFHE 1.6.1. The OpenFHE-enabled Release suite passes 14 tests on this Linux CPU environment. No CUDA execution or Hybrid rounding graph is claimed by that D7 result. D8 and D10's later architecture acceptance are documented below.

D8 complete: the Hybrid operation graph traces digit splitting, partial partitions, coefficient/evaluation transitions, noncanonical approximate CRT, full-key P offsets at reduced levels, B/A MAC ordering, exact CKKS ModDown, wrapper updates, and delayed QP operations. openfhe_hybrid_graph checks 18 full-size cases and 117,571,584 residue comparisons against independent unreduced-CRT and scalar formulas, including real generated keys and negative alternatives. The opt-in Release suite now has 15 CPU tests. Rotation automorphisms and higher-degree relinearization are source-traced but remain later end-to-end gates; production matrix coverage, GPU execution and performance are not claimed.

D9 complete: the device backend contract proposes immutable parameter snapshots, checked whole-tower views, device/session and generation identities, explicit stream/event dependencies, pinned resource lifetimes, cache identities, and an opt-in transactional DCRT format adapter. The portable metadata prototype is checked by backend_contract_check and a bridge to actual D8 OpenFHE output/key parameters. The opt-in Release suite has 16 CPU tests. Abstract interfaces compile without a CUDA dependency; CUDA resource management, event execution, caches and the adapter are not implemented. D10's acceptance is recorded below.

D10 complete: ADR 0001 accepts the D7–D9 behavioral contracts and the dependency-ordered implementation backlog. It freezes the explicit DCRT adapter, validated no-op and preflight-only fallback, immutable outputs, registry/lease ownership, partial-submission quarantine, separate configurable memory budgets and fail-fast admission. The review accepts P1's architecture; it does not promote the abstract API to a runtime backend. The existing CUDA constructor gap, native build, exactness, profiling and all later implementation gates remain open backlog items. D11 is next; P2 has not started because a native GPU environment has not been provisioned here.

P1 exit gate:

  • NTT/DCRT (D7) and Hybrid (D8) representation, ordering, and active-tower transitions are explicit.
  • The exact pinned CKKS approximate-CRT and reduction order is identified (D8); broader production fixtures remain P4/P6 work.
  • Buffer views record ring size, Q/P towers, level, representation, ordering, device, stream, and event ownership (D9 proposal and host checks; runtime implementation pending).
  • The first integration seam and CPU fallback behavior are frozen by ADR 0001.
  • Architecture review accepted and implementation work has dependencies, observable acceptance criteria and explicit remaining runtime gates.

Dispatch policy:

invalid input or inconsistent format    -> error
valid same-format request               -> validated no-op
available + supported + verified        -> CUDA backend
unavailable/unsupported/unverified      -> CPU only if allowed before submission
busy/budget/allocation failure          -> visible resource error
submission attempted, then any failure  -> visible error; no automatic CPU retry

The opt-in adapter defaults to RequireDevice. See ADR 0001 for the accepted transaction, ownership, cache-budget and admission rules. Production integration remains a P8 gate.

P8 exit gate:

  • OpenFHE CKKS runs with Hybrid key switching through the GPU backend.
  • Original CPU tests and fallback remain green.
  • NTT, base conversion, relinearization, and rotation meet exact gates.
  • Constants and evaluation keys remain resident across operations.
  • All results identify hardware, clocks/power mode, driver, toolkit, compiler, commit, parameters, timing boundary, and correctness status.

P9 — risk reserve (D96–D110)¶

Use only for work that blocks a preceding exit gate:

  • OpenFHE rounding/reduction-order differences;
  • natural/bit-reversed ordering mistakes;
  • CKKS level/tower corner cases;
  • register spilling, shared-memory pressure, or poor occupancy;
  • evaluation-key memory pressure and cache eviction;
  • CUDA stream/event lifetime defects;
  • primary-GPU compiler or architecture problems;
  • cross-GPU dispatch regressions.

Do not schedule new features in the reserve. Cipher inference begins only after P8 is green; it is a separate plan covering model operators, rescaling, rotations, graph scheduling, accuracy, and end-to-end latency.
