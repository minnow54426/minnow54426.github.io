ntt-gpu · a beginner's field guide to the GPU port

How the NTT runs on a GPU.

Each GPU thread handles a butterfly pair. Blocks keep small tiles in shared memory so several stages run without repeated VRAM traffic.

target: RTX 5090 ring dimension: 4,096–65,536 256 threads per block
every cook, same step, own ingredient

The GPU plan in four steps

This is the whole design. The chapters below explain the hardware and show the current code.

1 · SPLITGive each independent butterfly pair to a GPU thread.
2 · LOADA block gathers one 256-value group into shared memory.
3 · COMPUTERun several stages locally, with a barrier between stages.
4 · REGROUPUse a far-pair pass and a near-pair pass to cover the full NTT.
Current status: correctness-first baseline. Results must match the OpenFHE-compatible CPU reference exactly. The strided pass is not yet coalesced, so “four logical movements” does not mean four efficient VRAM transactions.

01

CPU and GPU favor different work

A CPU is good at a few complicated tasks. A GPU is good at many copies of the same small task.

i.

The CPU: a few master chefs

Four to eight highly skilled cooks. Each one can do anything: chop, taste, adjust, change the plan mid-dish. Give one chef the whole recipe and they finish it alone — one dish at a time, but any dish.

ii.

The GPU: a brigade of line cooks

Sixteen thousand cooks, but each one simple. The strict rule: at any moment, every cook performs the same step of the recipe — on their own portion of ingredients. Want 5000 cooks all whisking? Blazing. Want one cook to quietly deviate and taste-adjust? Nearly impossible.

This model is called SIMT: many threads run the same instructions on different data. An NTT stage fits because every thread can apply the same butterfly formula to a different pair.

The NTT is that work, almost embarrassingly so. One butterfly: u + c·v and (u − c·v)·w, over and over, billions of times. One recipe step, ten thousand portions.

02

Six GPU terms

Six words run all GPU programming. None is deeper than "row", "shelf", and "roll call" — and the last column shows what each one is in this repo.

WordPlain meaningIn this repo
threadOne cook. Simple, follows the shared recipe, owns one portion of data at a time.we use T = 256 per block
blockA kitchen station: a fixed team of cooks who share a counter (see shared memory) and can synchronize with each other — and only with each other.one block owns one tile
gridAll stations laid out. Blocks live in a 2-D grid with an x and a y address — a built-in pair of numbers each block can read to know "which job am I".x = tile index, y = RNS limb
shared memoryThe station's counter: small, fast, and private to one block. This is where the group lives while its stages run.256 values = 2 KB per limb
global memoryThe central warehouse (VRAM): huge (24 GB on a 4090), slow, shared by everyone. Data starts and ends here.the whole polynomial, all limbs
kernelA function you write once that every thread of a launch runs — same code, each thread on its own slice. The word for "recipe" in GPU-speak.six kernels in ntt_kernels.cu

A barrier (__syncthreads() in code) is the station's roll call: every cook in the block must arrive before anyone leaves. Chapter 7 is about the one way to misuse it.

The design fact hiding in the last two rows: on-chip traffic is 40–50× the pipe into the chip — the entire reason the communication ladder (chapter 5) exists. Aggregate shared figures are order-of-magnitude estimates (per-SM path × SMs × boost clock); the ratio is the point, not the decimals.
// the first rows are one multiplication chain — the table explains itself:
4090:   128 SMs × 1,536 threads/SM = 196,608 in flight ÷ 256 (our T) = 768 of our blocks resident

Why 256 and not the max 1,024 per block: smaller teams = six independent stations per island instead of one — each with its own counter, its own faster roll call, and a scheduler free to mix them. Grids bigger than resident (2,560 blocks at 40 limbs) simply queue for freed seats: the "waves".
At N = 65,536 with 3 limbs, each pass launches 256 × 3 = 768 blocks. How many stay resident at once depends on threads, registers, shared memory, and the device's block limits; measure it instead of assuming one wave.
03

One stage has independent pairs

Recall the NTT's shape: at every stage, the list is chopped into pairs, and each pair goes through one butterfly. At N = 8, one stage = four pairs. Click a stage and watch who pairs with whom:

one stage at N = 8 · click a stage
Every element belongs to exactly one pair per stage — the four butterflies share nothing. Four cooks, zero talking, any order. The fourth button is pass 1 of the real port in miniature (chapter 4).

That "share nothing" is the entire secret. Because the pairs are disjoint, the four butterflies of a stage can run simultaneously, interleaved, in any order, on any cook — the final list is identical every time. A GPU stage is just: hand each pair to a cook, let them all fly at once, wait for the slowest, next stage.

Disjointness also buys locality: a stage with distance d only ever pairs values inside one 2d-wide group, so a group of 2k values owns its k smallest stages outright — the fact chapter 4 turns into the two-pass split, taken once with strided groups and once with contiguous tiles.

Hold onto that sentence — it is also why a plain CPU simulator, running the same stage bodies serially, can prove the whole schedule before any GPU is rented.

04

Split the NTT into two passes

So why not one giant block that does the whole transform? Size — a block's counter is capped at 48 KB, and the data is far bigger:

where "1.5 MB" comes from · why the data can't sit on one counter
1 value (one coefficient, one limb)   = 64 bits  = 8 bytes
one limb   = 2¹⁶ values × 8 bytes      = 524,288 B = 512 KB
this repo  = 3 limbs  × 512 KB         = 1,536 KB ≈ 1.5 MB
real FHE   = ~40 limbs × 512 KB        ≈ 20 MB  = 427× a block's whole 48 KB counter
More limbs ≠ harder: each limb is one independent column of the grid (the y address) doing the identical dance — real coefficients are thousands of bits, kept as ~40 machine-word residues, one transform each.

So how should a GPU run this? Walk the same road the port had to walk — four steps, each one forced by the step before:

①

How the CPU does it — and where it hurts

The reference (ntt.hpp) is one cook walking the list in order: stage by stage, pair by pair. At N = 8 that's four butterflies, one after another — even though chapter 3 proved they're independent. The picture below is the whole problem in miniature: same four butterflies, four units of wall time versus one. Fine at lecture size — but a real forward is 32,768 × 16 ≈ 524,288 butterflies per limb, ~21 million across 40 limbs. One cook at a few GHz drowns; that's the wall.

②

First GPU idea: every pair on a cook, everything from VRAM

Hand each pair of each stage to its own cook, all cooks at once, everyone reading and writing the warehouse directly. This works — and it is what a naive port does for every stage. But now count truck trips: every stage fetches its partners from VRAM and writes them back — one round-trip per stage per value, and there are 16 stages. The cooks spend their day at the loading dock (chapter 8's ladder: warehouse ≈ ×400 the counter). Arithmetic nearly free, delivery-bound anyway.

③

The hardware rule that shapes the fix — and the one choice we get to make

The fast counter is private to a block — 256 cooks sharing 48 KB — and nobody outside the block can touch it. So a stage can escape the warehouse on one condition: all its pairs must sit inside data one block can gather onto its counter. The group size is ours to choose; the port picks 256:

counter budget:   48 KB ÷ 8 bytes per value = up to 6,144 values per group
choose:           256 values  (= 2 KB of the 48) — and 65,536 = 256 × 256

Why 256 exactly? It must be a power of two, so groups always contain whole pair-groups with nothing straddling an edge. And at N = 65,536 it makes the bookkeeping symmetric: 256 groups of 256 values, twice over — once strided, once contiguous (rung ④). A 2 KB counter also leaves room for many blocks per SM side by side (chapter 2's table: hundreds resident).

④

That number is the pair distance d

Look at a pair's addresses when the list is viewed as a 256×256 grid (row = 256q + r): partners of a far stage (d a multiple of 256) have the same r — same column, different row — so each strided group {r, r+256, r+512, …} owns all far stages. Partners of a near stage (d ≤ 128) sit in the same row — a contiguous 256-tile owns all near stages. Two groupings, no third case.

Stated cleanly, the four steps compress into one rule — the one structural idea of this port:

the two-pass split · groups of 256, twice
PASS 1 — the strided groups  (d = 32,768 … 256)
→  256 groups {r, r+256, …} each gather to a counter, run 8 stages, scatter

PASS 2 — the contiguous tiles  (d = 128 … 1)
→  256 tiles of 256 each gather, run 8 stages, scatter

Both passes run the same butterflies as the CPU reference. Pass 1 handles far pairs; pass 2 handles near pairs. This is four logical value movements, but pass 1 currently uses strided, uncoalesced addresses, so the hardware may issue many more memory transactions.

05

Keep a group in shared memory

Global memory is the warehouse; shared memory is the counter. A shared-phase block does exactly four things:

one block, one group · the kernel's whole life
① 256 cooks gather 256 values (1 each)  ·  ② roll call — values land on the counter  ·  ③ eight butterfly stages, barrier between  ·  ④ carry the results back
Naive code reads and writes VRAM at every stage. The two-pass design loads and stores each group once per pass. That reduces logical traffic, but pass 1 still needs a coalesced transpose or Four-Step layout to make those accesses efficient.

A 256-value group uses 2 KB of shared memory per limb, leaving room for several blocks to reside on an SM. Actual occupancy on the RTX 5090 must be measured after register use and launch limits are known.

The same trick, taken twice

Notice what the tile trick actually was: a group of 2^k values hosts the k smallest-distance stages with zero outside communication. The port takes this trick twice — once with strided groups, once with contiguous ones — and that is the whole two-pass split:

one forward at N = 65,536 · two passes, four truck trips

Two things this shape fixes at once. The order differs from stage order only in grouping — the forward runs pass 1 then pass 2, the inverse runs the same ladder backwards. And every launch is self-contained: two kernel launches per forward (one per pass), each block needing nothing but its own 256 values.

06

Map the design to code

Everything above exists in the repo in three small pieces. First, the butterfly body itself — written once, in include/ntt/dev_core.hpp, with the loop arranged as "one cook's slice of the pairs":

// one DIF stage, one thread's slice — the same body the CPU simulator runs
NTT_DEV void dev_dif_stage(uint64_t* tile, uint64_t tile_len, uint64_t d,
                           uint64_t n, const uint64_t* pp, uint64_t q,
                           uint32_t tid, uint32_t nthr) {
  const uint64_t lg = log2_of_pow2(d);
  for (uint64_t p = tid; p < tile_len / 2; p += nthr) {  // MY pairs: start at my
    // thread id, stride by the thread count — chapter 3's disjoint pairs
    const uint64_t g = p >> lg, j = p & (d - 1);        // which group, which offset
    const uint64_t u = (g << (lg + 1)) + j, v = u + d;  // the pair's two slots
    const uint64_t x  = tile[u];
    const uint64_t cv = mul_mod(pp[d], tile[v], q);     // ladder constant ψ^d
    tile[u] = add_mod(x, cv, q);
    tile[v] = mul_mod(sub_mod(x, cv, q), pp[(n >> lg) * j], q); // twiddle
  }
}

Second, the pass-1 kernel — pure choreography around the stage bodies, in src/cuda/ntt_kernels.cu. One block owns one strided group, start to finish:

__global__ void dif_col_kernel(uint64_t* a, const uint64_t* pp, const uint64_t* q,
                               uint64_t n, uint32_t sub) {
  extern __shared__ uint64_t smem[];                          // the counter
  const uint64_t r = blockIdx.x;                                // x = which strided group
  uint64_t* al = a + (uint64_t)blockIdx.y * n;               // y = which limb
  for (uint32_t t = threadIdx.x; t < sub; t += blockDim.x)  // ① gather: value r+256t,
    smem[t] = al[r + (uint64_t(t) << 8)];              //    one per cook
  __syncthreads();                                            // ② roll call
  for (uint64_t delta = sub / 2; delta >= 1; delta >>= 1) {  // ③ the 8 far stages,
    dev_dif_col_stage(smem, sub, delta, n, pp, q, threadIdx.x, blockDim.x, r);
    __syncthreads();                                          //    barrier each
  }
  for (uint32_t t = threadIdx.x; t < sub; t += blockDim.x)  // ④ scatter back strided
    al[r + (uint64_t(t) << 8)] = smem[t];
}

The pass-2 kernel (dif_tile_kernel) is the same shape with a contiguous gather — it is this kernel with r + (t<<8) replaced by base + t, running the near stages with dev_dif_stage.

Third, the launches — where the grid's two addresses become the map of the whole problem. Remember RNS from the butterfly guide: the same transform runs once per limb (per prime), completely independently, so the y address is the limb:

// one forward = TWO launches (grid = x × limbs):
dif_col_kernel<<<dim3(256, num_limbs), T, sub * sizeof(uint64_t)>>>(buf, d_pp, d_q, n, sub);
dif_tile_kernel<<<dim3(n/256, num_limbs), T, 256 * sizeof(uint64_t)>>>(buf, d_pp, d_q, n, 256);
// pass 1: block (x=r, y=k) = strided group r of limb k — owns {r, r+256, …}
// pass 2: block (x=q, y=k) = contiguous tile q of limb k — owns 256q … 256q+255

Three limbs means the GPU runs the entire RNS transform as one wave of blocks — no loop over limbs anywhere on the host.

And the communication between stages — the part that makes or breaks a GPU program — is different in each phase, by design:

⇄

Between the two passes: the mix is pure data movement

Pass 2's inputs are pass 1's outputs, regrouped — strided scatter becomes contiguous gather. No thread waits on another explicitly: the two launches share one stream, and pass 2 cannot begin until pass 1's writes have landed in VRAM. The pass boundary and the kernel boundary are the same line.

⇄

Between stages inside a pass: the barrier, because partners swap

On the counter, the values your thread reads at stage d were written at stage 2d by different threads of your block — the crossing re-shuffles ownership every stage. That is the entire reason for __syncthreads() after each stage: all 256 cooks finish, then anyone may read.

∅

Between blocks: silence — and that is the design

Inside either pass, every block's 256 values are a self-contained problem — a strided group for pass 1, a tile for pass 2 — and no pair ever leaves them. The forward has factorized into 768 independent mini-transforms per pass that never communicate, which is why one launch finishes eight whole stages, and why the GPU can pack blocks onto SMs in any arrangement it likes.

07

Synchronize between stages

Two GPU habits bite newcomers, and both are already handled in the kernel — know them when you read it.

the roll call rule · why barriers sit between stages
a block is exactly as fast as its slowest thread — so keep everyone's work the same shape

Rule 1: the barrier is all-or-nothing

Every thread of a block must reach every __syncthreads(). Put one inside an if that only some threads take, and the others wait forever — a hung kernel. That is why our barriers sit between stage loops, never inside the pair loop: all 256 cooks finish their slice, then everyone crosses together.

Rule 2: idle cooks still attend roll call

At N = 64 the tile is 64 values — only 32 pairs — but the block still has 256 threads. Most cooks hold no pair. Their loop body simply does zero iterations (for (p = tid; p < 32; p += 256) never starts), and they walk straight to the barrier. Harmless — as long as they don't skip it. The repo's n=64 test fixture exists precisely to keep this edge honest.

08

Memory movement sets the pace

The whole design — tiles, phases, staging — is really one decision: which shelf does each number live on? The shelves differ by orders of magnitude:

cost to fetch one value · relative, order-of-magnitude
Log-scale bars — each gridline is ×10. Exact cycles vary by GPU generation; the gaps are what matter.

In kitchen terms: registers are in your hands, shared is on your station's counter, global is the warehouse across town, and copying from the host computer is a delivery truck. Our kernel's shape follows directly: start and end in the warehouse, stage the tile on the counter, keep loop counters and twiddles in hands — and never, ever truck data back and forth per stage.

This ladder is also why the multiply pipeline stays on the GPU end to end: two forwards, pointwise, one inverse, then one truck trip home.

09

Current baseline and next optimizations

Everything above is proven before any rental: the stage bodies live once in dev_core.hpp, compiled by a CPU simulator that must match the reference exactly — the rented GPU's gates then check only the thin kernel wrappers. One confession before you read the benchmarks: version 1 of the GPU arithmetic is deliberately unoptimized. The multiply inside every butterfly uses the same __uint128_t division as the CPU reference — because on the GPU that division is emulated: the hardware has no 128-bit divide, so the compiler builds one from ~a hundred instructions. Every butterfly pays it.

That is the right order of operations: make it right, measure the gap, then make it fast. The bench table's job is to quantify exactly how slow v1 is — the CPU reference column is right there in the same table. The fix (Barrett or Montgomery reduction: division-free modular multiplication, the standard trick every production NTT uses) swaps in later behind the same function signature, with its own dedicated cross-check.

The first RTX 5090 run answers one question: does every supported size match the reference exactly? Then benchmarks should isolate modular reduction, coalescing, radix, register pressure, and end-to-end transfer cost.

The design in one paragraph

Each thread computes butterfly pairs. Each block loads one group into shared memory, runs several stages with barriers, and writes the group back. A far-pair pass followed by a near-pair pass covers the full transform; x identifies the group and y identifies the RNS limb. The CPU simulator proves the schedule before GPU testing. The current baseline favors exact results over speed; optimization comes next through division-free modular reduction, coalesced data layout, higher radix, and device-resident pipelines.
