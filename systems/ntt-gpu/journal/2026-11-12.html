Define and accept the device backend architecture¶

D9 defines checked backend metadata; D10 accepts the architecture and implementation backlog, closing P1.

Outcome¶

Completed the D9 backend proposal. The roadmap advances to D10's architecture decision and implementation backlog. P1 remains in progress until that review accepts the proposal. This change implements host metadata checks and compile-checked abstract interfaces; a CUDA runtime backend and OpenFHE adapter remain proposed.

Reasoning¶

D7 fixes representation and D8 fixes the exact Hybrid graph. A pointer/length API would still lose the active Q prefix, full-key P offsets, exact roots, producer completion and ownership of scratch/key material. The design keeps those facts together in immutable snapshots and checked whole-tower views.

The first integration seam is an explicit opt-in DCRT format-conversion adapter. It uses a private host candidate and commits only after complete success. CPU fallback is allowed only during preflight; invalid data and runtime failures are errors. Immutable public inputs and fresh outputs simplify initial alias and concurrency rules, with possible device-to-device copies counted as a cost.

Changes¶

  • Added backend_contract.hpp: immutable parameters, canonical layouts, checked extents, allocation generations, operation layouts, dependencies, cache identities, retirement and hoist rules.
  • Added backend_api.hpp: proposed stream, completion, immutable polynomial, owned download, cache-budget and backend APIs. There is no runtime implementation or factory.
  • Added backend_contract_tests.cpp as the normal-build backend_contract_check CTest.
  • Extended the Hybrid gate to import real OpenFHE context parameters and compare active QP metadata/key offsets with actual Hybrid output and key towers at L=5,4,3,1.
  • Documented staging ownership, event waits, single-upload cache entries, resource pins, failure quarantine, out-of-place costs and Hybrid lifetimes. The existing raw-Impl CUDA constructor cleanup gap is still open.
  • Registered the English article, linked D5/D8 to it, updated build guidance, and prepared the website export with the existing readable theme and sidebar.

Verification¶

The portable contract executable passes 78 checks on Linux x86_64/GCC 14.2. The same test passes AddressSanitizer and UndefinedBehaviorSanitizer with no reported issues. Tests include invalid roots, canonical values, overflow, incorrect reduced-QP spans, stale generations, overlap, missing cross-stream waits, failed-resource retirement, changed cache identities and forbidden post-submission CPU fallback.

Final local verification:

  • All 16 OpenFHE-enabled Release CTests passed in 11.31 seconds, including the 78-check metadata gate and the existing 117,571,584-residue Hybrid gate.
  • All 23 documentation unit tests and 14 Node interaction/math tests passed.
  • The documentation build generated 25 HTML pages, including eight journal entries, and validated local links, fragments, assets and catalog coverage.
  • Chromium passed 100 page/width checks across all 25 notebook pages at 1440/1024/375/320px: English content, rendered formulas, no page-wide overflow, and no script or failed HTTP responses. D9's section links and search worked; its article, this entry, the roadmap and both introductory lessons passed computed text-contrast checks. The tracker displays D10. Desktop and phone screenshots of the new article were inspected.

Publication exports the source article and journal to the existing personal website, preserving section navigation and the shared design. Deployment and live verification follow the website push. These are CPU/metadata and browser gates; no CUDA compiler or real GPU is available in this environment, and no GPU correctness or performance result is claimed.

Open questions¶

D10 must accept the first seam, immutable API, copy cost, registry provenance, cache budget/backpressure, failure quarantine and ordered implementation backlog. Runtime tests still need allocation/upload fault injection, cache races, asynchronous error/drain handling, completion abandonment and host rollback. Production Hybrid conversion/key-family coverage remains later work.

Next step¶

Produce the D10 architecture decision record and actionable backlog, accepting or amending the D7–D9 contracts. Keep P1 open until that review is complete; then proceed to P2's named-hardware native CUDA exactness and profiling gates.

D10: accept architecture and close P1¶

Outcome¶

Accepted ADR 0001 and the implementation backlog. The roadmap now marks P1 DONE and points to D11. P2 remains NOT STARTED pending native GPU provisioning. This acceptance freezes behavioral contracts and implementation priorities; it does not implement or validate the CUDA runtime backend or OpenFHE adapter.

Reasoning¶

The D1–D9 evidence establishes stage/index arithmetic, exact representation, the pinned Hybrid graph and checked metadata. Review identified two design gaps that needed explicit decisions: resource admission limits, and resource ownership when work is partially submitted but event recording or handle publication fails.

The ADR retains pins before the first enqueue-capable call, preserves failed operation records without returned handles, and requires drain/quarantine rather than immediate reuse. It chooses separate configurable cache/device-workspace/ host-staging ceilings of 256/256/128 MiB, one initial stream and one adapter transaction per session, with fail-fast admission. These are conservative design limits rather than measured optimal settings.

The DCRT adapter remains the first integration seam. RequireDevice is its explicit default; invalid data and resource errors cannot silently fall back. Only valid unsupported/unavailable/unverified operations may use an explicitly permitted CPU route before submission. Candidate import precedes the pinned nonthrowing DCRT move commit. Upstream allocating noexcept operations and the shared FTT cache's missing root identity remain explicit limitations.

Changes¶

  • Added the accepted ADR with decisions, source/evidence traceability, alternatives, partial-submission/error semantics and P1 exit dispositions.
  • Added twelve dependency-ordered backlog items, B01–B12, each with phase, deliverable and observable acceptance criteria through P8.
  • Made constructor RAII/device/input validation a P2 prerequisite, and recorded the setup helper's missing benchmark-error propagation and default-build coverage as baseline-reporting work. No CUDA fix is claimed in D10.
  • Updated D5/D8/D9 cross-links, build guidance, catalog and roadmap. Historical D9 results above remain intact; the new ADR supplies the current acceptance.
  • Prepared both new English pages for the existing website, section sidebar, search and shared readable theme. Runtime code and kernels are unchanged.

Verification¶

Observed on Linux x86_64/GCC 14.2:

  • All 16 OpenFHE-enabled Release CTests passed in 11.41 seconds, retaining the 78 metadata checks and 117,571,584 Hybrid residue-array comparisons.
  • All 23 documentation unit tests and 14 Node interaction/math tests passed.
  • The site builds 27 HTML pages with eight journal entries and validates routes, fragments, assets and catalog coverage.
  • Chromium passed 108 page/width checks at 1440/1024/375/320px: English text, rendered formulas, no page-wide overflow and no script/HTTP errors. ADR and backlog section links/search worked. Focused contrast checks covered the new pages, current journal, roadmap and both introductory lessons. The homepage and tracker show D11, P1 DONE and P2 NOT STARTED.
  • Visual review found the four-column task table cramped on phones. A contained, keyboard-scrollable table preserves column widths; twelve task IDs link to their acceptance criteria. Four focused width checks passed after the change, including keyboard scrolling and task navigation. Desktop and phone screenshots of the ADR/backlog were inspected.

Both repositories are prepared for publication from this source revision. Deployment and public-file verification follow the website push. The review environment has no usable native CUDA/GPU execution path, so none of the later native implementation gates is marked done.

Open questions¶

B01 must establish an actual primary/control GPU environment. B02/B03 must resolve native compilation and lifecycle failures before correctness or benchmark claims. Runtime budget defaults need measured memory-pressure evidence; broad parameter/key coverage, multi-stream capability, adapter rollback and process failure handling remain implementation acceptance gates.

Next step¶

D11 / B01: record the provided GPU, driver, toolkit, compiler, source revisions, OpenFHE build and native architecture configuration. Then run B02's native build and baseline-safety work before B03 exactness and B04 profiling. P2 is ready to start, not completed by the D10 review.
