Project & setup

Build the CPU version first and learn which GPU results have been checked.

At a glance

  • You can build and test this project without a GPU. Start with the CPU commands and the eight-value debugging example.
  • The November 19 Ada run passed the resident chain and new arithmetic/conversion checks. The primary RTX 5090 test remains open.

Before you start: No GPU or prior project setup is required.

Need a picture first? Watch a butterfly share its work.

Detailed guide

This project builds exact GPU polynomial operations for CKKS, an encryption scheme that supports computation on encrypted data. Start with the Number Theoretic Transform (NTT), which makes polynomial multiplication easier by evaluating at special modular points. Next add base conversion, which changes the set of primes representing each coefficient, and Hybrid key switching, which uses these operations to change a ciphertext's key representation. Finally connect the GPU implementation to the OpenFHE cryptography library.

What works: the CPU reference and tested CUDA baseline agree with OpenFHE. A temporary Ada GPU run passed its selected native checks. The newer resident-chain prototype passes host tests and compiles for CUDA; it has not run on a GPU. Next: validate the current source on RTX 5090. RTX 4090 remains the planned control. The main workload has 65,536 coefficients.

Build & test¶

Requires CMake, a C++20 compiler, and Python 3. CUDA is optional and detected automatically.

cmake -S . -B build -DNTT_ENABLE_CUDA=OFF
cmake --build build -j
ctest --test-dir build --output-on-failure

These commands build the program and run its CPU tests. The tests check the arithmetic, transform, assignment of work, buffer lifetimes and saved reports. A separate, slower calculation checks small examples independently. Other tests use the full N=65536 size. To follow one butterfly, use the N=8 debugging example.

CUDA builds register additional tests labelled gpu. Run those on actual hardware; a passing CPU simulation or CUDA compilation cannot validate device barriers, driver failures or GPU speed. The preparation guide lists the current native checks.

Exact OpenFHE compatibility¶

The optional compatibility test uses this exact OpenFHE 1.6.1 revision: b59e1f291965f14fbee5172cd83a20f5b856204f:

bash scripts/openfhe_setup.sh

The optional CPU suite compares complete arrays with real OpenFHE operations:

Check Read more
Forward and independent inverse through NativePoly::SwitchFormat Representation, roots and tower packing
Hybrid digit extension, key multiplication and reduction Exact operation graph
Buffer metadata and resident-chain host behavior Backend contract and prototype

For the Hybrid tests, enable OpenFHE's public-key encryption module (PKE), select 64-bit native integers, and turn reduced-noise mode OFF. CKKS decryption returns approximate numbers, so a plausible decrypted answer could hide an array mismatch. These tests require the same values, positions and roots. Design decisions and remaining implementation work appear in the architecture decision record (ADR) and backlog.

To reuse an installation, configure with -DNTT_ENABLE_OPENFHE_COMPAT=ON and set CMAKE_PREFIX_PATH to its install prefix. OpenFHE is not required for the standalone build.

First session on a rented GPU¶

Finish the offline preparation first. On the GPU machine, use the chosen source revision and the installation directory of the required OpenFHE version:

bash scripts/autodl_setup.sh

The helper records the machine and software versions, builds the code, and checks the answers. It also runs sanitizer tools, which detect memory and threading errors, before collecting 280 GPU measurement jobs. The jobs cover N=4096–65536, 30/50/55/60-bit primes and 1–40 RNS towers. A tower is one copy of the polynomial modulo one prime. Public-call and device-event timings stay separate.

Use NTT_REPO_DIR, NTT_CUDA_ROOT and NTT_OPENFHE_PREFIX for machine-specific paths. --resume --output-dir <record> reruns checks and reuses only matching, hash-verified measurements. --profile requests Nsight captures. The helper does not pull source, install dependencies or change drivers. Failed stages return nonzero; retain the complete record directory. See the collector guide for timing scopes and options.

Collect the matching 140-job CPU baseline locally without a CUDA installation:

python3 scripts/gpu_session.py --mode cpu \
  --openfhe-prefix build/openfhe-compat/install \
  --benchmark --output-dir bench-results-local-cpu

Use the same problem sizes and repetition counts in CPU and GPU sessions. The reports still identify each machine and build separately. Direct GPU collector commands default to the combined 420-job selection; choose --benchmark-scope gpu for GPU-only work. Changing modes or scopes requires a new record directory.

The default build targets sm_89 and, with CUDA 12.8+, sm_120. For one known GPU, use -DCMAKE_CUDA_ARCHITECTURES=native (CMake 3.24+).

Default CUDA uses one OpenFHE-style group twiddle per butterfly, with the same two-pass thread mapping. Configure a separate build with -DNTT_CUDA_LEGACY_BUTTERFLY=ON for the old two-multiply baseline. GPU JSONL records identify the choice as group_twiddle_ct or legacy_dif. The November 19 paired run measured both schedules on a server reporting RTX 4080 SUPER / compute 8.9.

Design¶

The resident operation-chain prototype adds polynomial handles whose inputs cannot be changed, one ordered GPU work queue (a stream), and temporary CPU buffers owned by the session. A limited operation log retains resources needed by unfinished work. Its CPU driver and CUDA adapter pass exact OpenFHE comparisons. The November 19 native Ada batch also passed the selected sanitizer checks. Production OpenFHE integration remains planned.

The November 20 resident basis-conversion addition composes ModUp and ModDown without intermediate polynomial downloads. Its CPU/OpenFHE and failure checks pass, and both CUDA schedules compile. That new composition still needs its own native GPU and sanitizer run.

Both backends use the same negacyclic transform convention:

psi is a primitive 2N-th root modulo q; psi^N = -1
forward: A_j = sum_i a_i * psi^((2j+1)*i) mod q
input: natural coefficient order; output: bit-reversed evaluation order

The CUDA schedule views each tower as a 256×256 array. Pass 1 gathers columns, whose elements are 256 positions apart; pass 2 loads rows of adjacent elements. Each pass handles eight stages using memory shared by a thread block. One forward transform launches two kernels and reads/writes the full array twice. Column accesses do not combine efficiently into memory transactions, so counting array bytes alone does not measure traffic to GPU memory.

Stage bodies in transform_stage.hpp are compiled for both CPU simulation and CUDA. The current __uint128_t remainder arithmetic is a correctness baseline. Shoup/Barrett reduction, coalesced layouts, and register staging are planned optimizations, subject to exact checks and profiling.

Use the work-distribution explorer to inspect blocks, threads, pairs, and twiddle exponents.

Docs¶

Start with NTT and butterflies, then CPU to CUDA. The implementation survey and GPU comparison explain the design choices.

python3 -m venv .venv
.venv/bin/python -m pip install -r docs/requirements.txt
.venv/bin/python scripts/build_docs.py --check
python3 -m http.server 8000 --bind 127.0.0.1 --directory build/docs-site

Open http://127.0.0.1:8000/. See writing and publishing for editing, journals, and GitHub Pages export.

Provenance¶

Independent clean-room implementation. No code, data, or artifacts from past or present employers. Development history is recorded in git.

Separate profiling executables use pinned NVIDIA NVTX C API headers, distributed under their upstream Apache 2.0 license with LLVM exceptions. The ordinary benchmark executables do not enable this instrumentation.
