CUDA execution · a worked example

One polynomial.
Two passes. Many threads.

See how our 4096- and 65536-point forward NTTs distribute data and butterflies. Start with what a block owns, then zoom into what a thread does.

01

Start with the data

Consider one polynomial modulo one prime: a[0], a[1], …, a[4095]. Each residue is an unsigned 64-bit integer. The flat array occupies 32 KiB.

4096coefficients per modulus
12stages · 2048 butterflies each
24,576butterflies · two kernel launches

Imagine the same array as 16 rows × 256 columns. This is only a way to read the indices—we do not allocate a matrix or transpose the array.

global_index = row × 256 + column
02

Divide the work by distance

Pass 1 · far stages

One block owns one column

2048 → 1024 → 512 → 256

These distances preserve the index modulo 256. Each block gathers 16 strided values into shared memory, executes four stages, and scatters the results back.

256 blocks per modulus. Every block launches 256 threads: 16 load/store values, but only 8 compute butterflies at each stage.

16 values · 128 B shared memory / block
Pass 2 · near stages

One block owns one row

128 → 64 → 32 → 16 → 8 → 4 → 2 → 1

These butterflies stay inside an aligned 256-value row. Each block loads its contiguous row into shared memory, executes eight stages, and writes it back.

16 blocks per modulus. All 256 threads load/store values; 128 compute butterflies at each stage.

256 values · 2 KiB shared memory / block

These are stages of one 4096-point transform, using its twiddle factors—not independent smaller NTTs. This page shows our current baseline schedule, including its inactive threads.

Pass 1: column 3, thread 5

Block 3 gathers values[3 + 256 × t] into shared[t], for t = 0…255. Thread 5 loads position 1283. At global distance 32768 (local distance 128), it computes shared positions 5 and 133: global positions 1283 and 34051. At distance 256 it computes 2563 and 2819 instead.

Pass 2: row 3, thread 5

Block 3 loads positions 768…1023. At distance 128, thread 5 computes 773 and 901; at distance 1, it computes 778 and 779. These indices match N=4096, but the global N used to select twiddles differs. The final row, block 255, owns positions 65280…65535.

Read the memory access map

In pass 1, adjacent loading threads access global addresses 2048 bytes apart (256 × 8 bytes), but write adjacent 8-byte entries in shared memory. The scatter reverses this mapping. In pass 2, adjacent threads read and write adjacent 8-byte global entries. Each block loads once, reuses shared memory across all its stages, and stores once.

Two reads and two writes of the value array give a logical minimum of 4 × N × 8 bytes per forward transform: 128 KiB at N=4096 and 2 MiB at N=65536, excluding twiddle/modulus reads and host transfers. This is requested array traffic, not measured DRAM traffic. Strided accesses, caches, registers, and occupancy need real-GPU profiling; 128 active butterfly threads out of 256 is not a hardware occupancy measurement.

Source map: CUDA kernels and launchers define the grid and gather/scatter; stage helpers map threads to pairs. For either size, the gather uses r + 256 × local_index; near-stage access uses row × 256 + local_index. Within each stage, every position belongs to exactly one butterfly.

04 · D2

Why these inputs and twiddles?

Our forward butterfly has two multipliers. Let ψ be the primitive 2N-th root modulo the current prime q. The ladder multiplier is c = ψ^d; the difference-leg multiplier is w = ψ^E. Both are powers from the global transform, not a smaller column NTT.

a = values[U]; b = values[V]
values[U] = a + c × b                 (mod q)
values[V] = (a − c × b) × w           (mod q)

1. Decode a thread into a local pair

The split width B is 256. Column r is blockIdx.x; p is the butterfly index. For both sizes, each active thread processes just one pair per stage, so p = threadIdx.x. More generally the stage helper loops over p = threadIdx.x + k × blockDim.x. Let δ be the local distance; the global distance is d = B × δ.

g = floor(p / δ)                     local butterfly group
j = p mod δ                          offset within that group
u_local = 2 × δ × g + j
v_local = u_local + δ
U = B × u_local + r
V = B × v_local + r = U + d

2. Recover the CPU group and offset

Substitute the local pair into the global index:

U = B × (2δg + j) + r
  = 2dg + (Bj + r)
CPU group start = 2dg
J = Bj + r                           CPU offset within the group

Because 0 ≤ j < δ and 0 ≤ r < B, we have 0 ≤ J < Bδ = d. Thus U and V are exactly the CPU pair at offset J in group g. Conversely, every CPU offset has a unique decomposition J = 256j + r. Together with p = gδ + j, this gives one unique column/thread owner for every CPU butterfly.

3. Prove the exponent, not just the result

The CPU starts w at 1 for each global group and multiplies it by ψ^(N/d) after each offset. At offset J it therefore uses w = ψ^((N/d)J). Substitution gives:

c = ψ^d
E = (N / d) × (256j + r)
w = ψ^E

This is precisely the stage helper: if ℓ = log2(δ), then δ << 8 = d, N >> (8 + ℓ) = N/d, and (j << 8) | r = 256j + r. The OR equals addition because r occupies only the low eight bits. Also 0 ≤ E ≤ N − N/d < N, so the power-table access is in range.

A subtle point: thread 0 in column 3 has J = 3, not 0. Its w is generally not 1. Only J = 0 gives exponent 0. The ladder c and w are distinct: the negacyclic ladder remains even when w = 1.

5. An exhaustive executable check

column_mapping_tests.cpp enumerates every CPU group/offset in every column stage for both sizes. It executes the actual dev_dif_col_stage body with synthetic tagged power tables. An upper-input probe reveals the selected w exponent; a lower-input probe checks the ladder and both destinations. Whole-column comparisons catch unintended writes. The test also checks unique coverage and every inactive thread.

There are 8,192 column butterflies at N=4096 and 262,144 at N=65536: 270,336 pairs and 540,672 active-pair probes. Tagged tables are diagnostic values, not valid root powers. The separate schedule gate checks real-root forward arrays, round trips, and multiplication. Both checks run on CPU; neither validates CUDA launch behavior or GPU races.

cmake -S . -B build
cmake --build build --target ntt_column_mapping_tests ntt_device_sim
ctest --test-dir build -R 'column_mapping_check|device_schedule_check' --output-on-failure

06

What keeps the work ordered?

Inside a block

All 256 threads reach __syncthreads() after loading and after each stage—even threads without a butterfly. This barrier synchronizes only that block.

Between the passes

The kernels use the same CUDA stream, so pass 2 starts after pass 1 finishes. Blocks within a pass are independent; SM scheduling does not guarantee they all execute simultaneously.

For CKKS with multiple RNS primes, repeat this arrangement per limb. Storage is limb-major: values[limb × N + index]. blockIdx.y selects the limb; blockIdx.x selects the column in pass 1 or the row in pass 2.

The mental model: a block owns a data subset; a thread computes a butterfly within it at each stage.
