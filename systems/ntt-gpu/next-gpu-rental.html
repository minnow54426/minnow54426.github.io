Next GPU rental queue

Run the prepared RTX 5090 checks, measurements and evidence export as one bounded batch.

At a glance

  • Both NTT versions passed the November 19 native Ada checks and compiled for sm_120.
  • The new batch prepares 64 measurement jobs and 48 sanitizer commands, followed by ordered repeats, profiles and a verified archive. RTX 5090 acceptance remains open.

Before you start: Finish offline preparation and use fresh directories for the next hardware run. Read Before renting a GPU first.

Detailed guide

Status: the expanded batch passed on November 19 on a server reporting RTX 4080 SUPER / compute 8.9. Both schedules also compiled for sm_120. The results and CUDA timeline were copied to the M1 Pro and verified. RTX 5090 hardware acceptance remains open. The queue below can be reused for that device after the next group of changes is ready.

The paired Ada analysis is complete on the M1 Pro. The November 21 conversion benchmark adds both ModUp input formats, independent ModDown, their resident composition and two host-boundary controls.

The November 20 resident ModUp/ModDown composition is a later source change. Its extended resident_cuda_exact fixture and --smoke cases must pass on the next GPU run. The earlier native result covers standalone conversion and the earlier resident NTT chain. See the conversion guide.

  • The collector runs two versions: the new group-twiddle schedule and the older, or legacy, schedule. It checks that both use the same inputs and GPU, and saves each version’s results separately.
  • The resident benchmark checks each result against an exact CPU product. The deferred host driver exercises the protocol and labels its output as simulation. The native collector rejects that output.
  • An independent CPU calculation matches the selected OpenFHE version’s ApproxModUp and ApproxModDown operations. These change the set of primes used to represent a polynomial. Tests use N=65,536, one to five active Q primes and three auxiliary P primes. The reusable converter now also has a broader all-dimension CPU comparison and prepared CUDA correctness probes. See conversion preparation.

One rental, ordered GPU work¶

Order GPU-only item Evidence to bring home
1 Preflight the actual RTX 5090, toolkit, driver, and profiler tools Device identity, commit, build options and tool versions
2 Verify the new default CUDA path and resident chain Native exactness against pinned OpenFHE, lifecycle/failure checks, and the NTT/resident smoke scopes under all four sanitizers
3 Verify the legacy control build before timing Native exactness and appropriate sanitizer smoke, with separate binary hashes and logs
4 Check Shoup and approximate basis conversion Native integer and pinned OpenFHE comparisons, plus all four sanitizer tools
5 Compare legacy versus group twiddles on matched inputs Raw paired resident forward/inverse samples first; public-call timings reported separately
6 Measure the resident operation chain and capture a selected profile End-to-end chain versus an intentionally host-roundtripped chain; device timeline and hardware counters if permitted

Run the queue as one batch¶

gpu_rental_batch.py combines the queue into one command. Preview its plan on any CPU machine; this prints JSON and does not build, contact a provider or run GPU work:

python3 scripts/gpu_rental_batch.py --mode plan

Before renting, compile both schedules for RTX 5090 and run their host tests:

python3 scripts/gpu_rental_batch.py --mode offline \
  --cuda-root /path/to/cuda --openfhe-prefix /path/to/openfhe \
  --build-dir build/rental-offline --output-dir bench-results-rental-offline \
  --budget-minutes 120

On the rental, use a clean checkout with pinned OpenFHE already installed. Select the physical index shown by nvidia-smi. The batch verifies RTX 5090 and compute capability 12.0, then selects that GPU by UUID for CUDA:

python3 scripts/gpu_rental_batch.py --mode gpu --device-index 0 \
  --cuda-root /usr/local/cuda \
  --openfhe-prefix build/openfhe-compat/install \
  --build-dir build/rental-5090 --output-dir bench-results-rental-5090 \
  --budget-minutes 120

Use fresh build and output directories. This command reuses the collector below, with eight workloads and four measurement scopes per schedule: 64 measurement jobs and 48 sanitizer commands across both schedules, in addition to their native exactness tests. It then runs a representative resident NTT case in legacy/group/group/legacy order, using five warmups and 50 samples per run. The small repeat controls run order; it does not replace the workload sweep.

Clock and temperature logging spans the session. Four independent profiler commands use separate NVTX profiling binaries to capture a timeline and limited counters for resident NTT and ModUp/ModDown. Their fingerprints are saved separately from benchmark binaries. Missing tools or blocked counters leave separate failure logs and produce GPU_BATCH_PASSED_WITH_LIMITATIONS if the required checks and measurement analysis pass. A profiler returning without a capture file is also a recorded limitation. The timelines label setup, warmups, samples, verification and cleanup; counter captures select ntt-gpu@ntt.sample/ and at most eight kernels. Inspect the operation nested inside a sample rather than whole-process totals. Instrumented output is rejected by the benchmark validator. Compile and check these profiles offline.

The budget covers preflight, compilation, checks, timings and profiles; it is a cutoff, not a runtime estimate. Each collector command shares the remaining budget. At expiry or a required failure, subsequent dependent GPU work stops. Cleanup and evidence packaging continue. The script does not stop provider billing: end the rental after exporting and verifying its evidence.

Read and export the batch record¶

The batch preserves partial records on failure or interruption. Its files are:

File What it establishes
batch.json Source/device preflight, overall status and separate profiler results
paired/ Both schedules' exactness, sanitizer logs, raw samples and matched workload index
controlled-repeat.json Ordered repeats, binary fingerprints and raw-log hashes
analysis/ Revalidated operation comparisons and separate repeat CSV
clocks.csv Device telemetry, when available
SHA256SUMS Fingerprints of the saved evidence files

After stopping telemetry, the script creates a sibling .tar.gz archive, checks every archived file against its source bytes, and writes .tar.gz.sha256 and .tar.gz.verify.json. It performs no extraction and refuses to overwrite previous records. OFFLINE_READY explicitly means no GPU execution. A verified archive may contain a failed run: read batch.json and both child reports before accepting its results.

Copy the archive and checksum to the local machine, then verify:

shasum -a 256 -c bench-results-rental-5090.tar.gz.sha256

The commands below remain available for a manually controlled session.

Use a small first timing block: N=4,096 and 65,536; K=3 and 40 towers; 30- and 60-bit primes. These choices give eight workloads per build. Use the same thread layout, modular arithmetic, random-input seed, warmup count and measurement count for both versions. Record GPU clock speeds. If temperature changes affect the results, repeat with the versions run in the opposite order. Expand to 50/55-bit primes and the remaining dimensions only after the required block is saved. The small timing block does not replace the full native exactness matrix.

Commands to prepare before provisioning¶

The compiler-only CI matrix builds pinned OpenFHE and both schedules for sm_89 and sm_120, including the new native test executables, with no driver. For a local dry run that also links pinned OpenFHE, use a Linux host with the toolkit installed:

python3 scripts/gpu_session.py --mode offline --compare-ntt \
  --architectures 120 --cuda-root /path/to/cuda \
  --openfhe-prefix /path/to/openfhe \
  --build-dir build/ntt-ab-offline --output-dir bench-results-ntt-ab-offline

On the rented GPU, confirm that the selected device is the RTX 5090 (compute capability 12.0) and that the driver and toolkit work before timing:

nvidia-smi --query-gpu=index,name,compute_cap,driver_version --format=csv
nvcc --version
compute-sanitizer --version
nsys --version
ncu --version

In a separate terminal, record clock and temperature readings while the collector runs. Stop the clock log when the collector finishes.

nvidia-smi --query-gpu=timestamp,index,temperature.gpu,clocks.sm,clocks.mem,power.draw \
  --format=csv -l 2 > bench-results-ntt-ab-5090-clocks.csv

From a clean checkout of the verified revision, use fresh directories for the native eight-shape sweep:

python3 scripts/gpu_session.py --mode gpu --compare-ntt --benchmark \
  --architectures 120 --cuda-root /path/to/cuda \
  --openfhe-prefix /path/to/openfhe \
  --build-dir build/ntt-ab-5090 --output-dir bench-results-ntt-ab-5090 \
  --benchmark-dimensions 4096 65536 --benchmark-towers 3 40 \
  --benchmark-prime-bits 30 60 --benchmark-scope gpu-conversion \
  --benchmark-warmups 2 --benchmark-samples 10

This selection records 32 measurement jobs per build, including eight conversion jobs. Every conversion sample is checked against pinned OpenFHE. Fixed NTT session setup is excluded. Per-call conversion parameter construction and upload, allocation and host orchestration are included. The final checks for resident operations download outside their timers. The two host controls include their boundary transfers.

The conversion selection also runs its benchmark at N=4,096/K=40/60-bit, one warmup and two samples, under all four sanitizer tools. Those instrumented times belong to correctness logs. The paired timing sweep starts afterward.

Both child runs include the new arithmetic and conversion probes. A conversion failure is retained with its test output and prevents timing that build. Both child runs must pass their exactness and sanitizer gates before their own timings. comparison.json only reports matched runs when the two manifests agree on the environment and the actual workload records match (including the roots and seed). The two sets of raw records stay separate. The collector finishes the default schedule before starting the legacy one. Temperature or clock changes between runs could therefore affect the comparison, even with matching inputs. Use --ntt-schedule to collect separately controlled repeats or a separate profiler capture. The combined command takes fresh directories and does not resume or profile. One failed child does not erase the other child's results.

Capture the resident timeline and export evidence¶

After the default branch of the paired run passes, reuse its build and N=65,536/K=3/60-bit vector. Run the timeline and hardware-counter captures independently so a counter permission failure cannot cost the timeline. Use fresh output names if you repeat a capture.

records=bench-results-ntt-ab-5090
binary=build/ntt-ab-5090/group_twiddle_ct/ntt_resident_profile
vector="$records/group_twiddle_ct/benchmark-vector-n65536-k3-b60.txt"
timeout 180 nsys profile --trace=cuda,nvtx --sample=none --cpuctxsw=none \
  --output "$records/resident-timeline" "$binary" "$vector" 1 2 \
  > "$records/resident-nsys.log" 2>&1 || echo "$?" > "$records/resident-nsys.exit"
timeout 180 ncu --nvtx --nvtx-include 'ntt-gpu@ntt.sample/' --set basic --launch-count 8 \
  --export "$records/resident-counters" "$binary" "$vector" 1 2 \
  > "$records/resident-ncu.log" 2>&1 || echo "$?" > "$records/resident-ncu.exit"

Profile timings stay separate from benchmark samples. On the Linux host, move the clock log into the record directory, then archive it:

mv "$records-clocks.csv" "$records/clocks.csv"
tar -czf "$records.tar.gz" "$records"
sha256sum "$records.tar.gz" > "$records.tar.gz.sha256"

Copy both files to the M1 Pro and verify before ending the rental:

shasum -a 256 -c bench-results-ntt-ab-5090.tar.gz.sha256
tar -tzf bench-results-ntt-ab-5090.tar.gz > /dev/null

When to rent, and when to stop¶

Before renting, confirm that the code compiles for sm_120, the RTX 5090 architecture, without requiring a GPU driver. Set a rental time budget and check that the provider allows the profiling tools and counters you need.

Run correctness before timing. If a required gate fails, save the failure evidence and skip timing that build. If counters are unavailable, record that limitation separately and continue independent checks or timings. End the session after the planned work (or budget cutoff) once raw logs, measurements and profiles are copied locally and their hashes verified. Review results offline, then choose which NTT path to carry into GPU base conversion. See collector details and the integration roadmap.
