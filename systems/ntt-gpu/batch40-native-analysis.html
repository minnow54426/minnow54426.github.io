Full-matrix GPU run: analysis¶

2026-11-14 · temporary reported RTX 4080 SUPER / sm_89 · CPU: local M1 Pro

The implementation passes the executed exactness and sanitizer gates. Its largest performance opportunity is currently the boundary around GPU work: keeping intermediate arrays resident already provides a substantial benefit. This is a measured baseline, not a finished OpenFHE accelerator or an RTX 5090 result. No new rental is needed to analyze or prepare the next experiments.

1. Correctness: a strong baseline, not complete FHE¶

The saved native run passes 29/29 CTests, including six GPU-labelled tests. The original OpenFHE comparison matrix records 169,279,488 residue comparisons; the expanded 140-cell × seven-pattern matrix records 3,967,746,048. These are comparison counts, not billions of independent random test cases. Independent inverse checks avoid relying only on a forward/ inverse roundtrip.

All eight sanitizer executions pass: memcheck, racecheck, initcheck and synccheck, each on legacy plus expanded matrix smoke. Both racechecks report zero warnings/hazards. Expanded smoke covers N=4096/65536, 30/60-bit primes, K=3/40 and zero/dense inputs: 107,790,336 comparisons per tool. It does not cover every possible input, concurrent context, allocation failure or stream ownership scenario. Setup-fault injection covers the existing ten pre-call injection points, not a guarantee about every real driver/OOM failure.

The fresh benchmark also validates its GPU outputs against the reference. The conclusion is exactness for the executed NTT/product cases against the pinned OpenFHE 1.6.1 path, not completed GPU base conversion, Hybrid key switching or CKKS inference. See the roadmap.

2. Public latency versus resident execution¶

All following numbers are medians in milliseconds, not minima or means. Public calls include host residue validation, guards, pageable transfers and blocking output copies. Public multiply also includes its by-value host copy/ output allocation. Setup/table construction is excluded.

Resident CUDA-event experiments exclude preparation/upload and result checking/ download. Multi-launch intervals still include submission gaps. The two scopes are separate experiments: their ratio is not a measured production speedup, and their difference cannot be labelled pure PCIe overhead.

3. Fusion is already a measured improvement¶

The complete unfused and fused chains are both directly timed under the same public-call protocol. Fused is faster in all 140 workloads. The per-cell unfused/fused median-latency ratio ranges from 1.77× to 3.03×, with a median of 2.36×. At N=65536/K=40/60 bits it is 2.69×.

This is transfer/API fusion, not butterfly-kernel fusion. Both chains launch eight kernels: two per forward, one pointwise, three for inverse including normalization. For one polynomial buffer of size S, the wrapper reduces operand transfer payload from 9S to 3S and reduces repeated validations/guards. Source accounting is explained in CUDA dataflow.

Consequently, preserve residency when designing base conversion and Hybrid key switching. Returning to the host after every NTT would discard an already demonstrated benefit. This does not predict a 2.36× Hybrid or inference gain.

4. Transfer scale, kernel trace and remaining bottleneck uncertainty¶

At N=65536/K=40 one u64 array is 20 MiB. The separately measured pinned copy events at 60 bits are:

Direction Median Effective payload rate
H2D 1.614 ms 12.99 GB/s
D2H 1.558 ms 13.46 GB/s

Rates use payload bytes / event time, decimal GB/s, not measured DRAM bandwidth or a claim about the PCIe link generation. The smaller 4096/K=1 copies achieve only about 5.4 GB/s because per-copy overhead matters. Public calls use pageable host vectors; these pinned-copy times are not an additive decomposition of their timings. In particular, 1.723 ms resident product time is not a promised end-to-end time for an input that still lives on the host.

The selected Nsight Systems trace uses N=65536/K=3/60 bits, one warmup and two samples. It is a different workload and profiler-perturbed observation, not a replacement timing series. Of its approximately 0.845 ms total kernel time:

  • Forward strided/contiguous kernels account for 29.5% / 26.7%.
  • Inverse strided/contiguous kernels account for 20.2% / 18.0%.
  • Pointwise and inverse scaling account for about 2.8% each.

These totals aggregate different operations and invocation counts. They are not percentages of one ring product. Total copy time in this trace is about 5.349 ms, but includes event reset/upload and validation/download that are excluded from resident timing. It must not be used as a production bottleneck percentage.

Compile-time resources are 40 registers for forward-strided, 38 for the other three transform kernels, and 24 for pointwise/scale, with zero spill loads/ stores. This does not establish achieved occupancy or utilization.

Nsight Compute fails with ERR_NVGPUCTRPERM; counters are unavailable. We therefore cannot yet rank modular reduction against strided memory transactions, barriers or occupancy as the dominant resident-kernel bottleneck. The current mul_mod uses u64 operands and a u128 remainder; specialized exact reduction is a candidate experiment, not a measured winner. Host validation/copy/staging costs also need separate timing.

5. Thirty-bit results and scaling¶

Thirty-bit primes currently use exactly the same u64 storage and arithmetic implementation as wider primes. They neither halve transfer size nor select a dedicated u32 modular kernel.

For each of 35 matching N/K pairs, divide the 60-bit resident median by the 30-bit median. The median ratio is 0.882 for forward and 0.881 for fused product; all 35 ratios are below one. In this run, 60-bit resident execution is about 12% faster by that paired-ratio summary, not slower.

Do not conclude that wider primes are intrinsically faster. Prime values and seeded residues differ; runtime remainder lowering may be input-dependent; widths ran in fixed order; clocks and active-load telemetry were not captured throughout the batch. The explanation remains unverified. Test a proven u32 implementation separately and repeat with interleaved/randomized order before claiming a 30-bit advantage or diagnosing the cause of this inversion.

At 60 bits, increasing N from 4096 to 65536 at K=40 grows resident product latency from 0.295 to 1.723 ms (5.83×) while N grows 16×. Increasing K from one to 40 at N=65536 grows it from 0.0852 to 1.723 ms (20.22×). This is consistent with fixed launch costs and improved use of parallel work at larger shapes, but does not prove the occupancy mechanism or predict scaling beyond K=40. Small shapes remain important: at N=4096/K=1 the M1 CPU product is faster than the public GPU product for both displayed widths.

6. CPU comparison and measurement reliability¶

The CPU path is OpenFHE 1.6.1 NativeVector/CRT-FTT, sequential tower execution, OpenMP OFF and native optimization OFF, built with Apple LLVM 21. It is not a best-tuned parallel DCRT/HEXL or CKKS application baseline.

At N=65536/K=40/60 bits, CPU/public-GPU ratios are 2.61× for forward and 5.28× for product. Across the matrix, the M1 CPU takes longer than the public GPU in 114/140 forward cells and 136/140 product cells. These are cross-platform latency comparisons, not same-host acceleration factors, architecture rankings or proof that one GPU is the most suitable purchase.

Only one ordered run per cell was collected. The 100 samples are repetitions within that run, not 100 independent sessions; p5/p95 describe sample spread, not confidence intervals. Do not overinterpret close differences:

  • Largest 60-bit public fused product: median 12.431 ms, mean 13.817 ms, p5 11.963 ms, p95 20.732 ms.
  • Its resident product: median 1.723 ms, p95 1.728 ms.
  • Across operation/cell pairs, median p95/median is 1.068 for public GPU, 1.013 for events and 1.107 for CPU. Some cells have much larger tails.

There are non-monotonic public results, e.g. 60-bit forward N=16384/K=16 is 1.786 ms while K=24 is 1.348 ms. This is a reason to repeat/control the experiment, not choose a dispatch boundary from this single noisy series. Resident curves are smoother, but kernel counters and repeated sessions are still needed to explain them.

7. Next work, without keeping a rental running¶

  1. Make split collection routine. Add explicit GPU-only/CPU-only scope selection and platform provenance to the normal resumable collector. The existing legacy --benchmark still schedules CPU timings on the GPU host.
  2. Prepare resident-pipeline experiments. Keep strict validation at the external input boundary, represent validated device buffers explicitly, and measure chains without repeated host roundtrips. Do not remove validation from untrusted public inputs to manufacture a speedup.
  3. Prepare one-factor kernel candidates offline. Prove u32/30-bit and u64 reduction bounds against bigint/reference/OpenFHE tests; separately prepare the coalesced-layout candidate. Do not change both together and attribute the result to either one.
  4. Freeze a bounded next rental batch. Include original baseline versus each candidate, exactness and sanitizers, repeated/interleaved timing order, active clocks/power metadata, and the same 30/50/55/60-bit/K≤40 matrix. Check counter permissions early; use the actual RTX 5090 for primary-device acceptance. Counter access may require a different rental environment.

No mathematical implementation changes or new GPU executions were made for this analysis. Remaining OpenFHE base-conversion, Hybrid and integration gates are unchanged. The daily journal tracks the evidence and the backlog tracks subsequent implementation.
